# ADR-008: 采用事务性 Outbox 与幂等消费者

- 状态: Accepted
- 日期: 2026-10-09
- 决策者: ForgeMesh 架构组
- 相关: architecture.md 第 2、12、13 章；development-plan.md 1.2、5.3、WP-1.6

## 背景

系统需要在更新业务状态的同时发布领域事件（例如资源分配成功、工作流步骤完成）。如果在数据库写入和消息发布之间做两次独立操作（"双写"），二者不是原子的：可能状态已更新但事件丢失，或事件已发但事务回滚，导致下游不一致。此外，消息系统通常至少一次投递，重复消费必须被安全处理。

## 决策

**采用事务性 Outbox（Transactional Outbox）与幂等消费者**：

- 业务状态更新与待发布事件的**写入在同一数据库事务中完成**（Outbox 表）。
- 由独立的发布器读取 Outbox 并投递到事件系统；投递成功后标记。
- **消费者按 `event_id` 去重、幂等处理**，重复投递不产生重复副作用。
- 关键业务事件**不得依赖非原子双写**；外部事件的到达只触发协调，不被无条件视为真实状态。

## 后果

**正面**

- 状态与事件保持最终一致，避免丢事件/脏事件。
- 至少一次投递 + 幂等消费 = 可靠的端到端语义。
- 支持控制器/服务崩溃后的安全重放。

**代价与约束**

- 需要 Outbox 表、发布器与消费去重存储，增加存储与运维成本。
- 消费端必须具备幂等性设计（稳定业务键/`event_id` 去重）。
- 需处理 Outbox 积压、发布延迟与顺序保证等边界情况（开发计划 13.2）。
