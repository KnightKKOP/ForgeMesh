# ADR-014: 对外 API 采用绑定租户的 API Key 认证

- 状态: Accepted
- 日期: 2026-10-12
- 决策者: ForgeMesh 维护者
- 相关: ADR-005、ADR-012；architecture.md 3.1（L1 Access Layer）、11.1（多租户边界）、14.1（基础原则）；v1.1-development-plan.md D1.1；SECURITY.md 第 4 节

## 背景

v1.0.x 中租户身份完全来自客户端可以随意填写的请求头，没有任何凭证校验：

- 网关 `Authz` 只检查 `X-Tenant-ID` 是否存在并原样采信；`AuthzWithToken` 只检查 `Authorization` 非空，不验证内容。
- 控制平面直接读取 `X-Tenant-Id` 作为租户，并且可以绕过网关被直接访问。
- 网关限流键取自同一个租户头（以及可伪造的 `X-Forwarded-For`），换一个头值就换一个令牌桶。
- 流式代理把调用方的 `Authorization`、`Cookie` 原样转发给推理实例。

结果是任何能访问网关或控制平面的人都可以读写任意租户的资源。这与 architecture.md 11.1（租户上下文必须在 API 边界验证）、14.1（最小权限、默认拒绝、租户间严格隔离）不符，也与 v1.0 发布记录"内置 API Key 与 OIDC 认证"的表述不符。

备选方案：

1. **OIDC / JWT**：需要外部 IdP 或签名密钥的分发与轮换；网关硬约束只用 Go 标准库，自行实现 JWS 校验成本高、风险大。适合作为后续扩展，而不是第一道防线。
2. **mTLS 客户端证书**：适合服务间调用，不适合终端调用方，证书签发与吊销的运维成本高。
3. **网关认证，控制平面信任网关注入的头**：控制平面仍可被直连绕过，违背网关 README 职责边界中"控制平面复核租户、不信任单点"的约定。
4. **只保存摘要的静态 API Key，绑定租户与 scope，网关与控制平面各自校验**（本决策）：两端都只需标准库，没有外部依赖，且可以独立验证。

## 决策

**对外 API 默认采用绑定租户的 API Key 认证，网关与控制平面各自独立校验同一份 key 文件。**

1. **凭证**：`Authorization: Bearer <key>`，scheme 大小写不敏感。key 由 `python -m forgemesh.controlplane.keygen --tenant <租户> --subject <主体>` 生成（`fmk_` 前缀 + 256 bit 随机数），只在生成时显示一次。
2. **key 文件**：JSON，网关（`GATEWAY_API_KEYS_FILE`）与控制平面（`FORGEMESH_API_KEYS_FILE`）使用同一格式，只保存 key 的 SHA-256 摘要：

   ```json
   {"keys": [{"id": "acme-ci-bot", "sha256": "<64 位十六进制>", "tenantId": "acme",
              "subject": "ci-bot", "scopes": ["read", "write"]}]}
   ```

   - 字段只认上述 JSON 名称；未知字段、重复 `id`、重复摘要、未知 scope 都是配置错误，服务拒绝启动。
   - `scopes` 省略时为 `["read", "write"]`；`[]` 表示没有任何权限；`null` 非法。
3. **租户来源**：租户只来自 key 绑定的 `tenantId`。请求可以不带 `X-Tenant-Id`；如果带了，任何一个取值与 key 绑定的租户不一致都返回 `403 FORBIDDEN`，而不是静默改写到另一个租户。网关在转发前把租户头覆写为已验证的值。
4. **授权（scope）**：`read` 允许读接口（GET）与推理调用（`/api/v1/namespaces/{ns}/inference/{svc}/chat` 与 `/api/v1/inference/{svc}/chat`）；`write` 允许写接口（POST / DELETE，包括启动工作流与请求决策）；`*` 表示全部。控制平面对每个端点检查 scope；网关对推理路由检查 `read`，使命中 Resolver 缓存、不经过控制平面的请求同样受约束。
5. **纵深防御**：控制平面不假设请求一定经过网关，自行校验凭证。网关把调用方的 `Authorization` 转发给控制平面（资源反代与 Resolver 查询），但**不**把 `Authorization` / `Cookie` 转发给推理实例。
6. **默认拒绝**：两端默认 `apikey` 模式，缺少 key 文件即拒绝启动；未知模式拒绝启动，绝不退化为信任请求头。控制平面应用未注入认证器时，受保护端点返回 `503 AUTHENTICATOR_UNAVAILABLE`。
7. **开发模式**：`dev`（`GATEWAY_AUTH_MODE=dev` / `FORGEMESH_AUTH_MODE=dev`）直接信任租户请求头，视为拥有全部 scope；只允许监听回环地址，启动时打印警告。
8. **错误语义**：缺少凭证或凭证无效返回 `401 UNAUTHENTICATED`，并携带 `WWW-Authenticate: Bearer realm="forgemesh"`；租户不一致或 scope 不足返回 `403 FORBIDDEN`。响应体为统一错误信封 `{"error": {"code", "message", "correlationId"}}`；所有不匹配的 key 都返回同一条 `invalid credentials`，不泄露 key 是否存在。
9. **限流键**：网关按已验证的租户限流，不再读取租户头或 `X-Forwarded-For`。

接口契约：

- 网关：`middleware.Authenticator`（`Authenticate(*http.Request) (Principal, error)`），实现为 `APIKeyAuthenticator` 与仅供开发的 `HeaderAuthenticator`；`middleware.RequireScope(scope)`。
- 控制平面：`forgemesh.controlplane.auth.Authenticator` 协议（`authenticate(headers) -> Principal`），实现为 `ApiKeyAuthenticator` 与 `HeaderAuthenticator`；FastAPI 依赖 `get_principal` / `require_read` / `require_write`。
- OpenAPI：`components.securitySchemes.apiKey`（HTTP bearer）作为全局 `security`，探针 `security: []`。

## 后果

**正面**

- 租户身份从"客户端声明"变为"凭证绑定"：伪造 `X-Tenant-Id`、直连控制平面、更换租户头绕过限流都被关闭。
- 两端只依赖标准库，没有外部 IdP；key 文件只含摘要，文件泄露不会泄露 key。
- `Principal`（subject / tenantId / scopes）与 `Authenticator` 抽象为审计归属以及后续的 OIDC / mTLS 提供统一接入点。

**代价与约束（破坏性变更）**

- 与 v1.0 "major 版本内保证 API 兼容"的承诺（ADR-012）冲突：对此前不带凭证的调用方，默认要求凭证是破坏性变更。本 ADR 认为租户隔离缺陷属于安全修复，优先于兼容承诺；`dev` 模式只用于本地过渡，不能作为生产环境的兼容开关。
- 默认模式下没有 key 文件的部署无法启动；本地开发需要显式选择 `dev` 模式（网关 `make run-dev`）。
- 不带凭证的请求由 `400`（缺少租户头）变为 `401`；网关的 `401` 响应体由纯文本变为 JSON 错误信封；推理实例不再收到调用方的 `Authorization`。实例如需凭证，应由网关以服务端配置注入，另行设计。
- key 没有过期时间；轮换或吊销需要同时更新两端的 key 文件并重启（暂不支持热加载）。
- 认证失败的请求不进入限流。256 bit 随机 key 无法暴力猜测，但入口洪泛防护仍需由前置负载均衡或 WAF 承担。

**后续事项**

- OIDC / JWT 与 mTLS 作为新的 `Authenticator` 实现，另行 ADR。
- key 文件热加载、过期时间与最近使用时间。
- 审计事件记录 `Principal.subject`。
- docker-compose / Kubernetes 示例以 Secret 挂载 key 文件。
