## 0. 范围与读法

- [v1.1-development-plan.md](v1.1-development-plan.md) 完成之后，#5–#23 又分三批实施：#5–#11 修复数据正确性并加上认证与控制器，#12–#16 打通推理服务的最小闭环，#17–#23 补齐资源的生命周期、可观测性与工程化。本文把这三批记为阶段 1 至阶段 3，后续的工作从阶段 4 开始编号：
  - **阶段 4：执行面与 MaaS 基础**。多节点执行、多副本，以及按模型名提供 OpenAI 兼容接口、配额与计量。
  - **阶段 5：生产规模与正式版**。PostgreSQL 与多副本控制平面、插件隔离、LoRA、prefill / decode 分离，最后做正式版评估。
- 每个阶段分成若干迭代，每个迭代由若干主题组成。一个主题对应一个分支与一个 PR，较大的主题拆成几个叠放的 PR。同一迭代内的主题如果没有标注依赖，可以并行开发。
- 本文不估算工期：每个主题写明内容、依赖与验收，规模以涉及的组件与改动范围描述。
- **状态口径**：计划中 / 进行中 / 已完成（附 PR 编号）/ 待定（需要维护者决定，见第 6 节）。目前所有主题都是“计划中”。
- **维护**：每合入一个 PR，更新对应主题的状态；新发现的遗留问题写进第 7 节并指定归属；设计细节写进 ADR 或组件文档，本文只保留结论与链接。

## 1. 现状：1.1.0 具备什么

| 领域 | 已具备（PR） | 尚未具备（归属） |

### 3.2 迭代 4.1：执行面基础

| 主题 | 内容 | 依赖 | 涉及组件 |
|---|---|---|---|
| 4.1-A Node Agent 网络传输（ADR-009） | 拆成 3 个叠放的 PR：① 由 `api/protobuf/agent.proto` 生成代码，`AgentServer` 与 `AgentClient` 之间改走 gRPC，控制平面与节点之间使用 mTLS（每个节点一张证书）；② 心跳与离线检测：节点超时转为 `NotReady`，其上的实例变为 `Unknown`，断线重连后查询并恢复未完成的任务；③ 节点经心跳上报设备（`gpu-nvidia` 的发现结果），作为调度器的清单来源，静态清单保留为可选来源，设备变化不再需要重启控制平面 | — | `packages/node-agent`、`api/protobuf/`、调度器的清单来源、部署清单（证书 Secret） |
| 4.1-B 容器与 Kubernetes 启动器 | `container`：经 Docker / Podman API 在控制平面所在的主机上以容器运行实例，GPU 经 CDI 或 `--gpus` 分配。`kubernetes`：每个实例一个 Pod，经 device plugin 申请 GPU；控制平面需要创建 Pod 的 RBAC，ServiceAccount 因此要挂载 token。这两个启动器的实例由容器运行时管理生命周期，不需要进程启动器那样的实例记录文件 | — | `controlplane/deployment/`、`deploy/kubernetes/` |
| 4.1-C 网关韧性与压测基线 | 连接实例被拒绝时立即刷新这个服务的实例缓存；首字节之前换一个实例重试一次（仅限请求体可以重放的情况）；非流式路由设置 `ReadTimeout`；限流器分片，GC 移到后台；缓存过期时先返回旧值，同时在后台刷新；可选的 TLS。压测基线（首字节时延 P99、并发流数、控制平面写入吞吐）写进文档，并在 CI 中做回归 | — | `gateway/` |
| 4.1-D 协调与工作流持久化 | 审批决定与协调的退避计数（包括实例丢失后重新部署的退避）持久化，重启后不丢失；工作流运行结束时经 Outbox 事件通知控制器，取代每 2 秒一次的轮询，事件按资源保序投递；提供工作流运行的查询接口；Temporal Provider 实现 `find_run` 与步骤输出，能够运行部署工作流 | — | `controlplane/reconciler/`、`controller/`、`workflow-runtime`、`plugins/workflow-temporal` |
| 4.1-E span 与 OTLP | 记录 span 并经 OTLP 导出。OpenTelemetry SDK 作为可选依赖，未配置导出地址时不启用；`forgemesh.controlplane.observability` 中不经 `/metrics` 输出的内存记录器改为 `/metrics` 的实现或删除 | — | 控制平面、网关 |
| 4.1-F 发布流水线与类型检查 | 构建并发布镜像（推送到镜像仓库、签名、SBOM）；提供包含 vLLM 与 TGI 的 GPU 镜像变体；类型检查（mypy 或 pyright），先在控制平面包上严格执行 | — | `.github/workflows/`、`deploy/docker/` |

**退出条件**：控制平面与 Node Agent 作为两个独立的进程经真实网络联调，这项测试进入 CI；断网恢复后同一个任务不会重复执行；使用伪造证书的节点被拒绝。容器启动器进入 compose 冒烟。网关的压测基线写进文档。控制器不再轮询工作流运行。

### 3.3 迭代 4.2：多副本与运行时完善

| 主题 | 内容 | 依赖 |
|---|---|---|
| 4.2-A 多副本 | `spec.availability.replicas` 生效：调度器为每个副本分配加速器，每个副本一个部署运行，`status.endpoints` 列出全部副本，网关在 ready 的副本之间轮询；缩容时先摘除 endpoint，再停止实例 | — |
| 4.2-B 滚动更新 | 按 `maxSurge` / `maxUnavailable` 先起后停，加速器不够时退回先停后起；更新期间服务不中断 | 4.2-A |
| 4.2-C 应用层健康检查 | 按协议定期探测实例（如 `GET /health`），连续失败的副本从 endpoint 中摘除，再按实例丢失的流程重新部署；实例核对不再只看进程是否还在运行 | — |
| 4.2-D 远程实例与分配租约 | 新增经 Node Agent 在远程节点上启动实例的启动器；远程节点持有的分配带租约，节点失联超过租约时回收分配并重新调度 | 4.1-A |
| 4.2-E 真实 GPU 上的验证 | `vllm-process`、`tgi-process`、容器与 Kubernetes 启动器在 GPU 节点上跑通推理服务的完整闭环（创建、`Ready`、对话、更新、实例丢失、删除）；需要自托管的 GPU runner，或者把手工演练的记录写进文档 | 4.1-B |
| 4.2-F 按期移除已弃用的接口 | 列表接口的 `tenantId` 查询参数按弃用声明在 1.3.0 删除（OpenAPI 与实现一起删除，CHANGELOG 标注「破坏性」） | — |

**退出条件**：在假运行时上，3 个副本的服务被杀掉一个副本之后不中断服务，滚动更新期间的请求全部成功；至少一个真实运行时在 GPU 上验证过并有记录。

### 3.4 迭代 4.3：MaaS 接入层

| 主题 | 内容 | 依赖 |
|---|---|---|
| 4.3-A 插件接入应用 | 启动时按插件策略文件加载插件（新增环境变量）；决策插件接入决策路由，`/api/v1/decisions` 变为可用；计量与 QoS 插件接入策略引擎；插件注册时的制品摘要写入审计；受信任的公钥绑定插件 id，授予绑定签名者，支持密钥轮换与吊销 | — |
| 4.3-B 模型与 OpenAI 兼容接口 | 引入模型的抽象：新资源 `Model`，或者在 `InferenceService` 上声明对外的模型名（需要 ADR）。网关提供 `/v1/models`、`/v1/chat/completions`、`/v1/completions` 与 `/v1/embeddings`，按请求中的 `model` 路由到提供这个模型的服务；新协议 `openai-embeddings`；CLI 能管理模型。与 4.2-A 一起设计实例的选择：同一个模型可以由多个服务与多个副本提供 | — |
| 4.3-C 配额 | 按 API key 与模型的 RPM / TPM 配额，由网关执行，超出时返回 `429` 与 `Retry-After`。配额从哪里来（key 文件还是控制平面 API），以及多个网关副本之间如何共享计数，需要先定下来（ADR） | 4.3-B |
| 4.3-D token 计量 | 从响应与流（`stream_options.include_usage`）中读取用量，经计量插件追加 `UsageRecord`（租户、key、模型、输入与输出 token）；提供按租户查询用量的接口与计量修正事件；租户隔离覆盖计量 | 4.3-A、4.3-B |
| 4.3-E 认证的后续（ADR-014） | key 文件热加载、过期时间与最近使用时间，不重启就能轮换与吊销 key；按主体（而不只是按租户）限流；网关到控制平面使用 mTLS；webhook 请求签名；OIDC / JWT 作为新的 `Authenticator` 实现（另行 ADR） | — |

**退出条件**：OpenAI 官方 SDK 只修改 `base_url` 与 key，就能以流式与非流式调用 `/v1/chat/completions`；超出 TPM 时返回 `429`；计量记录与响应中的 `usage` 一致。

### 3.5 迭代 4.4：推理感知的路由、扩缩与分布式推理

| 主题 | 内容 | 依赖 |
|---|---|---|
| 4.4-A 推理实例的指标 | 采集实例的排队请求数、KV cache 占用与前缀缓存命中（vLLM / TGI 的 `/metrics`），由 Node Agent 或控制平面汇总，供网关与扩缩使用 | — |
| 4.4-B 推理感知的路由 | 网关的路由策略可以配置：轮询（默认）、最少排队、KV cache 感知、前缀亲和；接口参考 Gateway API Inference Extension 与 llm-d 的调度器 | 4.2-A、4.4-A |
| 4.4-C 自动扩缩 | 按推理指标（排队请求数、KV cache 占用、首 token 时延）在 min / max 之间调整副本数，带冷却时间；缩容到 0 作为可选项，并写明冷启动的代价 | 4.2-A、4.4-A |
| 4.4-D 分布式推理 | 一个实例跨多台机器（vLLM 的 Ray 后端，或多节点的张量并行 / 流水线并行），经 Node Agent 在多台机器上协调启动；调度器按拓扑分配 GPU（节点内张量并行、跨节点流水线并行，考虑 NVLink 与 InfiniBand 亲和）；部署工作流增加多节点的准备与验证步骤 | 4.1-A、4.2-D |

**退出条件**：在假运行时上能重复演示指标驱动的路由与扩缩；两节点的分布式部署在 GPU 环境中跑通，并有记录。

## 4. 阶段 5：生产规模与正式版

| 迭代 | 内容 | 依赖 |
|---|---|---|
| 5.1 PostgreSQL 与多副本控制平面（ADR-007、ADR-013） | 注册中心、Outbox、审计与工作流存储放进同一个 PostgreSQL 数据库，消除两个 SQLite 文件之间没有事务的问题；契约测试在两种后端上都运行；以有序的迁移脚本取代按 `PRAGMA table_info` 探测的迁移；SQLite 到 PostgreSQL 的迁移工具与演练文档；实现 leader 选举（例如 PostgreSQL advisory lock）之后允许多副本，只有 leader 运行控制器；ADR-013 更新状态 | 阶段 4 |
| 5.2 插件进程隔离（ADR-006） | 受限 RPC 宿主（子进程或容器），最小权限与出网白名单；清单的 `isolation` 支持进程与容器隔离，高风险插件必须隔离运行；性能基线 | 4.3-A |
| 5.3 LoRA 与模型目录 | 同一个基础模型上动态加载多个 LoRA 适配器，按 `model` 名路由到适配器；模型目录：版本、摘要校验（`spec.model.digest` 生效）、经 Node Agent 把权重预先下载到节点 | 4.3-B、4.1-A |
| 5.4 prefill / decode 分离 | 预填充与解码由不同的实例承担，KV cache 在实例之间传输，路由协调两者（参考 llm-d 与 AIBrix 的做法） | 4.4-B |
| 5.5 正式版评估 | 按 architecture.md 第 20 节逐项验收（见下表）；满足之后把 OpenAPI 的 `x-stability` 改回 `stable`，按弃用政策决定版本号，发布正式版的发布记录 | 5.1、5.2 |

**退出条件**：5.1 的两种后端都通过契约测试；在两个副本的控制平面中，leader 退出之后另一个副本接管，资源状态不丢失。5.2 的高风险插件只能在隔离宿主中运行。5.5 的验收表全部满足。

**正式版验收表**：对照 architecture.md 第 20 节，列出 1.1.0 尚未满足的条目与关闭它们的迭代。其余条目在 5.5 逐项复核。

## 5. 开发与迭代方式

- **分支与 PR**：一个主题一个分支、一个 PR；较大的主题拆成叠放的 PR，每个 PR 都能单独评审，描述中写明依赖与只含本 PR 改动的对比链接。
- **提交**：遵循 Conventional Commits，并签署 DCO；一个逻辑修改一个提交，每个提交单独检出时 CI 全部通过。
- **每个主题的流程**：
  1. 先确认设计，需要时写 ADR（Proposed，评审后改为 Accepted）；
  2. 实现：每个行为变化都有在旧代码上失败的测试；
  3. 扩展 compose 冒烟覆盖新功能；需要 GPU 的项目写明验证环境与演练记录；
  4. 同步 CHANGELOG、README、OpenAPI 与 module-mapping；
  5. 合入之后更新本文对应主题的状态。
- **破坏性变更**：API 稳定性为 `beta`，minor 版本可以包含破坏性变更，但 CHANGELOG 必须以「破坏性」标注并写明迁移方式（[弃用政策](../governance/deprecation-policy.md) 1.4 节）。已经声明的弃用按期移除。
- **版本**：建议每完成一个迭代发布一个 minor 版本（见第 2 节的表），由维护者决定。
- **验证环境**：CI 只覆盖不需要 GPU 的部分（假运行时）。4.2-E、4.4-D、5.3、5.4 需要真实 GPU：单机多卡，以及以 InfiniBand 或 RoCE 互联的两台机器。

## 8. 风险

- **Node Agent 传输是阶段 4 的关键路径**：4.2-D、4.4-D 与 5.3 都依赖它，证书的签发、分发与轮换需要先设计好。
- **多副本带来的一致性问题**：多个网关副本之间的限流与配额计数需要协调；5.1 之前控制平面必须保持单副本（ADR-013）。
- **真实运行时长期缺少 GPU 验证**：启动器的命令行参数与就绪检查可能与实际的 vLLM / TGI 版本不符，4.2-E 越晚，发现得越晚。
- **外部项目的接口变化**：vLLM 与 TGI 的指标名、KV cache 传输库与 OpenAI 接口的新字段都可能变化，相关代码应当集中在启动器与协议适配层中。
- **PostgreSQL 迁移**：需要数据迁移、双写过渡与回退方案，并在演练文档中验证。
