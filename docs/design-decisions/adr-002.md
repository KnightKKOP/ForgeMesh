# ADR-002: 采用声明式资源模型

- 状态: Accepted
- 日期: 2026-10-09
- 决策者: ForgeMesh 架构组
- 相关: architecture.md 第 2、5 章；development-plan.md 1.2、5.1、WP-0.1

## 背景

命令式脚本（"执行这一步、再执行下一步"）难以应对失败恢复、状态追溯和治理：一旦中途失败或外部状态被修改，很难判断当前究竟处于什么状态，也无法幂等地重放。AI 算力基础设施的资源生命周期长、外部因素多（节点离线、GPU 被占用、服务崩溃），需要一种能持续逼近目标状态、可恢复、可审计的模型。

## 决策

采用**声明式资源模型**，所有核心资源使用统一结构：

```yaml
apiVersion: forgemesh.io/v1alpha1
kind: InferenceService
metadata:
  name: llama-service
  namespace: team-a
spec:      # 用户希望达到的目标状态（Desired State）
  ...
status:    # 系统观察到的实际状态及其判断（Observed State）
  phase: Pending
  observedGeneration: 0
  conditions: []
```

关键约束：

- `spec` 与 `status` **严格分离**：用户写入 `spec` 表示目标；`status` 由控制器观察后写入，用户不可直接设置为目标。
- 通过 `metadata.generation` 标识目标配置版本，`status.observedGeneration` 标识控制器已处理的配置版本。
- 使用结构化 `conditions` 表达状态条件；使用 `metadata.resourceVersion` 或等价版本字段进行并发控制。
- **系统不得因为 `spec` 已写入就假定操作已完成**；实际状态必须由观察得到。
- 所有核心资源须有强类型定义与 Schema 校验，禁止以未校验的任意字典作为公共 API。

## 后果

**正面**

- 控制器可持续协调、幂等收敛，重复处理同一事件不产生副作用。
- 状态可恢复、可追溯，符合架构不变量二（目标与执行分离）与不变量四（可恢复、可追溯）。
- 资源以声明式 YAML 表达，便于版本管理与多环境复现。

**代价与约束**

- 需要实现持续协调的控制器闭环（9 步）并保证幂等。
- 需要处理 `generation`/`observedGeneration` 差异带来的中间状态与并发保护。
- 状态机不能"一个枚举打天下"，不同资源需各自定义状态流转。
